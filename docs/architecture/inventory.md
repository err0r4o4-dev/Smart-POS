# Inventory (Phase 2)

Phase 2.1–2.6 COMPLETED for local acceptance on 2026-10-09. Evidence is in docs/development/verification.md; this is not production readiness.

Inventory identity is organization + stock location + existing catalog Variant ID. Each location belongs to one branch. Stock may exist directly at any physical location; parent links organize navigation only. Aggregation sums each balance exactly once, never parent rollups plus child balances. Quantities are in the Variant's selected unit: exact NUMERIC(18,3), decimal strings in APIs; COUNT/PACKAGING require whole units. Conversion metadata is not automatically applied. Recorded stock is not sensor-observed physical stock. Unit-specific summaries never sum kilograms and pieces.

The immutable ledger is the stock mutation entry point. A database trigger locks/creates the balance, validates the delta and nonnegative result, fills before/after and increments version atomically. Runtime cannot write balances or edit/delete movements. An authorized organization transaction already locks the tenant row; commands serialize within a tenant before balance locks, preventing lost updates and inconsistent multi-item transfers. This deliberately conservative policy trades throughput for correctness; production load assessment is a separate gate.

Opening stock is allowed once per identity before any history and requires an elevated permission, reason and idempotency key. Adjustments use DRAFT -> PENDING_APPROVAL -> APPROVED -> POSTED, with rejection/cancellation before posting. Inventory staff may request, never approve/post. Owner/Manager may authorize within branch scope; this initial policy permits their own approval and records creator/approver/operator, without claiming mandatory separation of duties.

Counts capture quantity and version for explicitly selected Variants, including zero-stock identities. Physical entries do not mutate stock. IN_PROGRESS -> SUBMITTED -> APPROVED -> POSTED validates every captured version before applying variance. A stale count conflicts atomically; cancel and create a new snapshot/recount. Original evidence remains stored. No blind refresh or percentage division by zero.

Transfers use DRAFT -> PENDING_APPROVAL -> APPROVED. Same-branch dispatch posts paired movements and completes immediately. Inter-branch dispatch moves stock into a system-managed, transfer-specific IN_TRANSIT location belonging to the source branch. Full receipt moves transit stock to destination; no partial receipt is claimed. Dispatched transfers cannot be cancelled. Creation/approval require both branches; dispatch requires source access, receipt destination access. A receiver may inspect the transfer it participates in but cannot browse arbitrary source stock. All movement pairs share a command/reference and conserve quantity per Variant.

Reservations are not implemented: reserved is explicitly zero. Recorded on-hand excludes IN_TRANSIT; transit is separate. POS-eligible stock is active SALES_FLOOR/SHELF with active Product/Variant. Warehouse is movable but not directly sellable; QUARANTINE/DAMAGED/IN_TRANSIT are not sellable. Correction/evacuation of archived catalog stock remains possible through authorized workflows, never by deleting references. New opening stock requires an active Product/Variant.

Reorder thresholds evaluate active warehouse + sales-floor + shelf balances for one branch/Variant in its unit, excluding quarantine/damaged/transit. Minimum/target are exact with target >= minimum; thresholds can be deactivated. No AI recommendation, purchase order or accounting valuation. `/inventory/valuation` stays planned.

RBAC extends the existing fixed permission engine. All roles need active membership and branch assignments except Owner's organization-wide scope. Owner/Manager receive all inventory grants (Manager restricted to assigned active branches). Inventory staff receive read/audit, location management, adjustment requests, count create/update, transfer create/dispatch/receive and reorder management, not approval/posting/opening. Purchasing receives read, transfer create/receive and reorder management. Cashier receives read only for assigned branches. No global administrator is added.

Mutation idempotency binds organization + actor + operation/path + UUID key + SHA-256 canonical request payload. Exact retries return saved committed JSON; reused keys with changed payload conflict. Failed transactions do not reserve the key or leave partial writes. Authorization is rechecked before returning cached results. Inventory query keys include user/organization/branch/filter/page and are cancelled/isolated on scope changes.

All new tables FORCE tenant RLS and composite tenant/branch/object FKs. Application checks branch authorization independently. Definer trigger functions have fixed search_path, explicit tenant/user checks and revoked public execution; they are narrow ledger maintenance, not general privileged SQL entry points. Production needs separate migration/runtime LOGIN credentials; local privileged bootstrap credentials are not production-safe.

Phase 3/4 must invoke inventory application commands inside approved transactions rather than writing balances. SALE/PURCHASE_RECEIVE/reservations/cost layers are not public Phase 2 endpoints. No POS, purchasing, advanced shelf management or AI implementation is authorized here.

## Command and read policies

- INCREASE/DECREASE take positive delta magnitudes. CORRECTION takes an absolute nonnegative target captured against balance version at creation; stale posting conflicts. No ordinary ledger edit or automatic reversal endpoint exists: use a new authorized compensating adjustment or transfer, preserving original references/evidence.
- Count creation starts IN_PROGRESS directly (no separate scheduling/DRAFT lifecycle is claimed). Select 1–100 Variants, save observations while IN_PROGRESS, submit only with every observation, approve, then post. Counted quantity/version/actor/time and variance remain recorded. Zero baseline percentage is displayed as a dash, never infinity or divide-by-zero.
- Source/destination branches and physical locations must be active for new mutations. Receipt may drain a transfer's existing system transit location after its source branch becomes inactive, but destination branch/location must remain active. This dedicated settlement is not permission to mutate other inactive-source stock. Owner can inspect historical inactive branches; all such stock has zero POS-eligible availability.
- Locations can change type before first stock history only. Deactivation requires zero stock, no active child and no open document. System transit locations cannot be user-edited. Parent cycles and cross-branch/tenant parents reject. No deletion API.
- Quantity/status/location/category/product/movement/actor/date filters use bounded, parameterized queries. Form location options and catalog Variant choices are paginated, not limited to the first 100 identities. Arbitrary category/actor filters currently use UUID fields rather than rich autocomplete.
- Overview active_variants is explicitly an organization-wide active catalog count; recorded/low-stock/pending summaries are branch-scoped. Recent ledger is returned only with inventory.audit.read. Unit/type totals include transit as a separate type; never treat it as additional destination on-hand.
- Location create relies on org/branch/code uniqueness, update on current revision. Other inventory writes use org/actor/path/key/payload idempotency. Failed writes leave no operation result, balance, document-state or audit partial commit. No optimistic client stock updates.

## Operational limits and future integration

Commands serialize by tenant, so correctness is verified but high-throughput POS/load/deadlock performance is not certified. Idempotency/audit/transit records currently have no automated retention/cleanup job. Counting is restricted to explicitly selected Variants and a single location, not distributed sensor/shelf observation. Inter-branch receipt is all-or-nothing; no partial receiving, post-dispatch cancellation, return logistics or recall/batch/expiry tracking.

Phase 3 sales must call authorized inventory application ports atomically with sale/payment state and define reservations explicitly; Phase 4 purchases must atomically integrate verified receipts. Do not directly UPDATE balances, INSERT privileged stock rows from another runtime, convert unit metadata automatically or mix costing into the quantity ledger. Those phases remain NOT STARTED.
