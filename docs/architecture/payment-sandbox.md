# Stripe sandbox connection — first implementation slice

Date: 2026-10-12. This is a development-only connection diagnostic, not the completed single-store online sales flow and not production readiness.

## What exists

- Management page `/manage/settings/storefront/payments`, linked from storefront settings. Owner/Manager must still have active membership and `storefront.manage` on every API request. Writes retain existing allowed-Origin and CSRF middleware.
- Server-only `STRIPE_TEST_SECRET_KEY`, optional and disabled by default. Only `sk_test_` keys are accepted; live/publishable keys fail startup with a sanitized message. Configured sandbox is rejected when `APP_ENV` is not `development`.
- Stripe-hosted Checkout for one synthetic THB 20.00 item. Card and PromptPay are requested; actual availability depends on the Stripe test account. No customer/order data is copied into the test payment. Scope metadata contains organization/user identifiers and the explicit sandbox purpose.
- Create/retry uses a user+organization-scoped hashed idempotency key. Browser session storage retains the pending command key and current test Session ID per user/organization. Same-key retries must be prompt: Stripe's retention is not a permanent local idempotency ledger.
- Retrieve checks test mode, object, payment mode, exact amount/currency, organization, creator, sandbox purpose and Session ID. Only an HTTPS `checkout.stripe.com/c/pay/{id}` redirect is allowed. A success URL is never proof of payment.
- Full test refunds derive the PaymentIntent and amount from the verified paid Session. Refunds use a deterministic session-scoped idempotency key and return an existing scoped refund when present. Pending, requires-action, failed and canceled refunds are not displayed as successful refunds.
- No order changes, accounting entries, cash movements, sales, stock reservations, stock posting or fulfillment happen in these diagnostic routes. Stripe sandbox objects remain their test record; these routes do not write the separate customer payment persistence described below.

## Customer Checkout adapter foundation (2026-10-12)

This adapter is **internal and unrouted**, not a working customer payment flow. `config.Config.CustomerPayments` is constructed but is not passed to the router. The existing diagnostic still reports `customer_checkout_enabled=false`. There is no customer Checkout endpoint, HTTP webhook receiver, public prepaid POS action or customer payment button. The adapter-only checkpoint had no persistence; subsequent schema17–20 slices below add internal persistence, recovery and prepaid settlement without enabling customer routes.

- `STRIPE_CUSTOMER_CHECKOUT_ENABLED` defaults to false and accepts only the literal values `true`, `false` or an absent value. Enabling the adapter requires both the existing test key and `STRIPE_CUSTOMER_WEBHOOK_SECRET`. Customer test configuration is rejected outside development; error messages do not contain the credentials. These new variables are not forwarded by Compose yet. Setting them in an API process does not create a customer route.
- `CustomerCharge` accepts a validated organization/order/slug, integer THB minor units and a positive Unix expiry. Its local input range is THB 10.00–999,999.99. It does not calculate order totals, freight, discounts or an eligible creation expiry; the future orchestration must freeze those server-side and check the supported creation window before requesting Checkout. Retrieval can validate an expired attempt without changing its original expiry.
- The separate customer adapter requests card only, keeps the existing API pin, and uses order/organization-scoped hashed idempotency. Metadata distinguishes `online_order_test_payment` from the management diagnostic. Session validation checks exact frozen amount, currency, expiry, scope and expected Session ID, explicit test mode, payment state and PaymentIntent. Invalid responses return no usable Session object. HTTPS redirects must match the exact provider host and Session path; provider-owned fragments are allowed.
- Both return URLs contain only the public shop/order locator and neutral `payment_return=1`. No tracking access token or customer contact is sent to Stripe. The future browser flow must preserve private tracking access locally before redirect; a return flag never marks an order paid.
- Raw webhook verification uses HMAC-SHA256, constant-time signature comparison, a five-minute delivery timestamp tolerance and multiple `v1` signatures. Duplicate timestamps, oversized bodies/headers, malformed JSON, missing/test-mode flags and unusable Session envelopes are rejected. Only `checkout.session.completed` and `checkout.session.expired` are returned; unrelated authenticated event types are distinguished from invalid signatures. Signature verification alone is not frozen-order validation, settlement, event deduplication or durable acknowledgement.
- Turning off new Checkout does not turn off configured signature verification or provider retrieval for existing attempts. The shared transport makes no automatic retries, sanitizes upstream failures and now enforces the full 1 MiB response limit, including oversized trailing bytes.

## Durable payment persistence foundation (2026-10-12)

Forward migration `000017_online_payment_persistence.up.sql` adds `online_payment_attempts` and `online_payment_inbox`. That checkpoint required clean schema17; the subsequent hold slice below requires schema18. Earlier applied migrations are unchanged. The migration was exercised only on newly provisioned script-owned tmpfs PostgreSQL; primary migration/restart/deployment and retained-data schema16 upgrade acceptance were not performed. Deploying matching API source against an older schema will fail readiness until an explicitly approved migration rollout.

- `BeginCustomerPayment` checks the private tracking credential and configured single-store scope, then commits one attempt per organization/order from the immutable order total. Only reserved, unlinked, active-status orders in a published accepting store are eligible. The separate Checkout deadline is the earlier of one hour from creation and the original order deadline, rounded to exact Unix seconds; the database bounds it to 30 minutes–24 hours. Neither retries nor these tables change the order's original expiry, prices or stock source.
- The attempt freezes its organization/order/slug/THB amount/expiry and can bind only one globally unique test Session. `BindCustomerPayment` is a trusted internal provider-response seam, not a browser DTO or staff confirmation endpoint. It validates the full frozen charge and expected Session, but only records `OPEN`/`PROCESSING`; response binding alone never grants a terminal `PAID`/`EXPIRED` state. Do not call it with client-supplied provider data.
- `AcceptCustomerWebhook` authenticates the original body before tenant resolution, validates purpose/order/scope/session/amount/currency/expiry and event-state consistency, then locks organization before attempt. A canonical fingerprint of minimal payment evidence distinguishes exact replays from altered event identities; formatting and delivery-signature changes do not produce new evidence. Raw customer payloads, private access tokens, provider URLs and signing secrets are not persisted in the inbox.
- Event insertion, first Session binding and state projection share one transaction; success returns only after commit. An event can arrive before the create response because the frozen attempt already exists. Failed validation or state application is rolled back rather than acknowledged. The inbox is an append-only accepted evidence journal, not a running background queue or HTTP receiver.
- State precedence is `REQUESTED < OPEN < PROCESSING < EXPIRED < PAID`. Replayed/concurrent stale events cannot downgrade `PAID` or change its PaymentIntent. Same-Session paid evidence wins even if expiry arrived first, but **payment evidence alone never authorizes fulfillment** of an expired/cancelled/unfulfillable order. Such funds need later stock/reconciliation/refund handling, not automatic shipment or POS posting.
- Both tables have ENABLE/FORCE RLS and transaction-local tenant context. Composite/deferred foreign keys bind inbox rows to the final attempt Session; frozen-field/history guards prohibit charge/session drift and require inbox evidence for terminal transitions. Runtime grants do not permit inbox update/delete or attempt deletion. Database constraints enforce bookkeeping relationships; cryptographic/provider authentication remains the Go boundary's responsibility.

The persistence checkpoint performs **no provider create/retrieve calls**, stock posting, sale/cash accounting, customer-route wiring, UI/contract changes or Compose configuration forwarding. Paid evidence is not yet projected into tracking/POS. Payment-aware reservation guards are added below; external request/retrieval recovery and prepaid POS remain prerequisites before any customer payment capability is enabled.

The central stock ledger therefore continues protecting the same holds for competing writers. Quantity/quality checks and recall/disposal precedence remain unchanged; payment does not make unsafe stock saleable.
- `REQUESTED`, `OPEN`, `PROCESSING` and unreleased `PAID` retain stock beyond both provider and original order deadlines. Unknown creation outcomes are not evidence of nonpayment. - Only a committed transition to evidence-backed `EXPIRED` releases the payment extension. Terminal/cancelled orders never regain liveness from a webhook. Neither expiry snapshots nor immutable order deadlines are rewritten.
- Staff and direct runtime SQL cannot reject, cancel or expire an order with unresolved/paid payment state. Confirmed unpaid expiry permits ordinary cancellation. SQL guards enforce lifecycle consistency, not signature authentication.

This prevents collecting twice while prepaid settlement is unfinished. Unpaid orders without attempts retain their existing POS flow. No sale, stock posting, cash entry or provider tender is created by this slice.
- The migration conservatively marks already-expired attempts and already-dead unlinked orders as released rather than reacquiring their stock during upgrade. Backfill uses tenant context and requires a migration role able to bypass RLS; otherwise `row_security=off` fails rather than silently omitting protected rows. A retained-data schema17 upgrade has **not** been acceptance-tested and remains a rollout gate.

## Internal Checkout orchestration and retrieval recovery (2026-10-12)

Forward migration `000019_online_payment_recovery.up.sql` adds immutable `online_payment_dispatches` and append-only `online_payment_observations`, both ENABLE/FORCE RLS. This orchestration checkpoint required clean schema19; current readiness is schema20 after the internal prepaid slice below. No primary migration/restart, retained-data upgrade, real Stripe request or public-route enablement was performed.

- `CreateCustomerCheckout` authenticates private tracking access, commits the frozen attempt and dispatch marker, then calls the existing customer adapter outside the database transaction with a ten-second child deadline. A marker records intent to dispatch, not proof that the provider received it. Errors and interrupted response commits retain the same unresolved attempt/hold; no automatic retry loop or replacement payment identity is created.
- The stored request fingerprint is an HMAC covering the actual method/endpoint, unchanged API pin, unchanged scoped idempotency key and canonical form, keyed by the configured test credential. No key, tracking token, raw provider body or redirect URL is stored. Charge, return-origin, credential or request-identity drift fails closed for existing dispatches; credential/origin rotation is not silently authorized or reset by recovery.
- Unbound replay requires the same fingerprint, an eligible accepting storefront/order, more than 31 minutes until the original frozen payment expiry, and a dispatch age under 23 hours. These are application safety bounds, not a claim of provider acceptance. Retries never extend expiry. Concurrent callers may make identical provider requests under the same key; the implementation does not claim only one HTTP call or independently prove Stripe's idempotency guarantees.
- Once a Session is bound, create/retry switches to `RecoverCustomerCheckout` rather than creating again. Recovery performs an authenticated known-Session GET outside a transaction, independently validates the frozen charge/scope/Session, then atomically commits the minimal observation and monotonic attempt state. It still works when new Checkout is disabled, or when a known Session was bound by webhook without a local dispatch row. Recovery rechecks private access before committing evidence.
- Observations use local UUIDs and source `CREATE_RESPONSE` or `RETRIEVE`; they never invent `evt_` IDs or populate the webhook inbox. Canonical snapshot fingerprints deduplicate identical observations. The service and SQL guards validate source/status/outcome consistency and immutable snapshot binding; runtime cannot rewrite or delete either journal. These constraints enforce bookkeeping, not cryptographic authentication of an arbitrary SQL insert.
- A create response binds only `OPEN`/`PROCESSING`, never terminal paid/expired state. Verified retrieval can supply terminal evidence. A paid create hint is nevertheless retained and prevents contradictory expiry from releasing a hold. Mismatched amount/intent or failed state application rolls back the observation. Stale retrieval cannot downgrade paid; late paid cannot restore a released extension or cancelled stock.
- A redirect is returned only from a validated open response after commit, while the persisted attempt is still open and unreleased. An early paid webhook suppresses a later create-response redirect. Neither a URL nor a browser return flag is payment evidence. No sale, stock posting, cash effect, prepaid POS path, customer tracking projection, public HTTP contract, Compose forwarding or payment button is added here.
- If creation is unknown and no Session is known after the safe replay window, recovery returns conflict and keeps the hold. It does not search unrelated provider Sessions, guess an ID, fabricate expiry, or release stock. A durable operational reconciliation/refund path for this unresolved case remains required before enabling customers.

## Local setup and test

1. Create/select a Stripe sandbox in your own account. Use synthetic contact/payment details only; do not scan a test QR expecting a real transfer.
2. Configure `STRIPE_TEST_SECRET_KEY` securely in the API process environment (or the ignored local Compose environment). Do not paste it into chat, a browser field, source control, test fixtures or screenshots. No `VITE_` payment secret is needed.
3. Run updated API/web only against an explicitly authorized development environment. Compose forwards the optional key, but changing the environment does not update an already running container. 4. With an authorized management account, open `/manage/settings/storefront/payments`. “ตั้งค่า test key แล้ว” means the local key exists, not that Stripe has been contacted successfully.
5. Create the THB 20.00 test Checkout, then open the returned Stripe page. Use Stripe's documented sandbox payment flow. Returning without paying must remain unpaid.
6. Use “ตรวจสถานะรายการใหม่” to retrieve provider status. Checking a test Session created by another user/organization/purpose must fail; changing the URL cannot make it paid.
7. After a successful test payment, explicitly confirm the full test refund. Refresh provider status; pending/requires-action must remain distinct from succeeded. PromptPay refund completion may require further provider-side action.
8. Inspect the test objects in the Stripe sandbox dashboard if an operation is ambiguous. Retry the existing command rather than inventing a successful result. An unconfigured key, provider outage, unavailable payment method or invalid provider response produces an error and leaves customer commerce unchanged.

Do not use actual payment credentials or customer data in sandbox tests. No external provider request was made during fixture-based unit/component verification.

## API

Prefix: `/api/v1/organizations/{id}/storefront/payment-sandbox`.

| Method / suffix                            | Behavior                                                              |
| ------------------------------------------ | --------------------------------------------------------------------- |
| `GET /` (prefix itself, no trailing slash) | Safe local status; `customer_checkout_enabled` is always false        |
| `POST /checkouts`                          | Empty JSON object and UUID `Idempotency-Key`; fixed test payment only |
| `GET /checkouts/{sessionId}`               | Authoritative scoped Session/refund status                            |
| `POST /checkouts/{sessionId}/refund`       | Empty JSON object; full scoped test refund only                       |

POSTs require the normal session, allowed Origin and CSRF token. All routes use `storefront.manage`. The adapter pins Stripe API `2024-06-20`, uses bounded HTTP/context timeouts, refuses redirects, bounds responses, does not retry automatically and never echoes raw provider/network errors or credentials. No SDK/dependency installation was required.
