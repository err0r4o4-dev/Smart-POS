# Explicit single-store deployment mode

Date: 2026-10-12. This document records the first completed scope slice after the Stripe connection diagnostic: one deployment is limited to an existing organization. Subsequent reservation/source/internal payment/refund slices now exist through clean schema23. The complete online flow is **PARTIAL / PAUSED by the user**, not enabled customer delivery/Checkout or production readiness. See [current cumulative status and policy](payment-sandbox.md#current-online-flow-status-2026-10-12); the verification below retains this slice's historical scope and counts.

## Configuration and boundaries

- Optional server-only `SINGLE_STORE_ORGANIZATION_ID` must be exactly one UUID. Invalid, comma-separated or whitespace-padded values fail configuration parsing without echoing the supplied value. UUID casing is normalized.
- Empty configuration preserves the existing multi-organization behavior. A configured UUID never selects the first organization, creates a new owner, merges organizations or changes memberships/data. Configure the intended existing organization explicitly; no production environment was changed by this implementation.
- The existing organization transaction boundary rejects other organization IDs before opening a database transaction, including callers that belong to both stores. Active membership, role permissions, branch assignments, RLS and CSRF/Origin checks remain required for the selected store.
- Organization listing includes only active membership in the configured store. A signed-in nonmember sees no store and must receive a valid invitation. Organization creation, including idempotent creation retries, is denied with 403 while single-store mode is active.
- An invitation resolving to another organization is rejected before membership/invitation changes. Invitations for the configured store retain current inviter, recipient, role and branch validation. Account registration never grants automatic store access.
- Public directory queries run with the configured transaction-local organization context and return only its published, active storefront or `[]`. Public slug reads, quote/order commands and tracking resolution reject other stores. Unpublished, missing or inactive selected stores never fall back to another store.
- Existing data for other organizations is retained and not migrated or deleted. This is an application deployment restriction, not a replacement for tenant authorization or a claim that the database contains only one organization.

## API and UI compatibility

- Directory JSON shapes are unchanged. `GET /api/v1/organizations` and `GET /api/v1/storefronts` add `X-SmartPOS-Store-Mode: single|multi`. The header includes no organization UUID, secret or permission grant.
- Management/account UI reads mode from the same successful directory response. Older servers without this additive header retain multi-store compatibility there. Public `/shop` opens the only published shop regardless of mode and no longer displays a shop selector. Invalid headers or multiple public directory entries are errors, not authority to choose a store.
- `/shop` opens the one configured published storefront directly. Management/account setup hides organization creation and organization switching; authorized branch selection remains available. Empty membership shows invitation guidance instead of a first-user setup form.
- Existing storefront purchases remain pickup-and-pay-at-POS. The single-store UI must not describe online payment or delivery as available until the later order/reservation/payment/shipment slices are integrated and verified.

## Activation and recovery

1. Identify the intended existing organization through an authorized owner account in the current environment. If there is no organization yet, complete the existing authorized first-store onboarding before enabling single-store mode; there is no anonymous bootstrap claim path.
2. Set `SINGLE_STORE_ORGANIZATION_ID` only in the API process environment or ignored local Compose environment. Compose forwards the optional reference; it does not apply changes to an already running process automatically. No frontend environment value is required.
3. Restart/rebuild only the explicitly authorized target. This source slice adds no migration and does not authorize `stack:up`, primary migrations, deployments or resets.
4. Verify selected-store membership, no additional-organization creation, rejected foreign URLs/invitations and public discovery behavior before rollout. A valid but nonexistent UUID deliberately produces no accessible/published store; correct the setting, never select a fallback store.
5. Clearing the setting restores the old multi-store presentation and API behavior without moving data. Environment/process changes still require their own authorization.
