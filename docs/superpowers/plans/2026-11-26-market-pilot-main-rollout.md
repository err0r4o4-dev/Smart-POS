# Market Pilot Main Rollout Plan

**Goal:** Show 13 market pilot storefronts and their 195 photographed menu items on the existing local SmartPOS gateway at `127.0.0.1:8088/shop`, alongside the existing storefront.

**Architecture:** Use the Go API and its existing tenant-scoped setup and publication controls to import the fixtures. Serve the approved covers as same-origin assets. Persist optional cover references through storefront settings and return them through the public directory and storefront detail. Keep the current business type and use food categories for discovery.

**Tech stack:** Go, PostgreSQL, React, and the existing local Docker Compose stack.

**Spec:** The approved 12-store pilot, the new made-to-order shop with 15 menus, and 195 distinct menu photos. The existing 12 covers are available; the new shop uses the established fallback until its cover is generated. The initial fixture plan remains scoped to the isolated pilot.

## Main cutover and recovery

- Establish the main Compose target and current schema read-only. Before cutover, confirm retained-data rollout scope, obtain independent review on a scoped redacted diff and matching test evidence, and demonstrate a backup and restore on an isolated target using the project's approved storage controls.
- Rehearse recovery using synthetic data only in a new loopback PostgreSQL 17 sandbox. Check that a custom-format dump is readable, restore only into an empty sandbox database with the required roles, and compare schema version, the sentinel storefront, exact menu prices and counts. Never use `--clean` against the retained database. For the main backup, agree the exact owner-only on-machine storage directory and retention window first. Keep the archive outside Git, public assets and third-party storage; do not log identities, contents or credentials. Verify the archive after creation and record the checksum and schema version. Take the main backup only after that procedure is authorized.
- Preserve the previous app image and use supported revision-checked settings to unpublish newly published stores first if verification fails. Use main-database restore only as a separate approved recovery operation, after assessing writes since the backup. Do not automatically overwrite the retained database or drop newly created records.
- Preflight evidence: port `8088` belongs to `smartpos-caddy-1` in Compose project `smartpos`. The public directory is in multi-store mode and lists one existing storefront. `smartpos-postgres-1` reports schema 53, clean, and zero storefront slug or organization code collisions for this package. No data writes ran. Repeat the checks immediately before cutover.
- Publish the matching app, migration and assets; import only the named 13 stores. Load and validate each store while unpublished. Once complete, publish with `accepting_orders=false`. Verify the original storefront and its menu still work and validate all 195 new SKUs, category labels, and image responses through `8088`. Check isolation with an unrelated account.
- Keep the pilot available during verification. If a cutover step fails, stop the rollout, preserve evidence, and recover using the reviewed rollback: take the new storefronts out of the public list using supported settings, restore the prior app/schema pairing as needed, and preserve the retained database. Only stop the three pilot listeners once the main storefront is verified; keep its data for recovery.
